CONTEXT ENGINEERING · 光溯产品设计与验证笔记

从自然语言到 Context Contract：企业 Agent 的产品建模

把自然语言组织成可执行的任务上下文。

2026.07.17 · 9 MIN READ

一句描述里缺失了什么

“它打不开了”包含了一个现象，却没有说明对象、时间、影响范围、已经尝试过什么，也没有给出能够验证的证据。人类专家会自然追问；Agent 需要把这种追问变成结构化的上下文构建。

让所有能力使用同一份任务事实

任务上下文应当为工具调用、知识检索、过程追踪和最终评测提供相同的基础：哪些是用户已确认的事实，哪些是系统推断，哪些仍需要补充。

核心原则证据不等于结论；模型的流畅表达也不等于任务已经完成。

人工确认不是补丁

当任务范围、敏感操作或最终处置会产生真实影响时，确认点应成为流程的一部分。这样既避免误执行，也把专业判断留在真正需要它的地方。

AGENT SYSTEMS · 专题与随笔

Harness 不是 Agent SDK：一张图理解模型之外的 Agent 工程

SDK 解决“如何调用模型”，Harness 解决“如何让一个 Agent 系统可靠地持续工作”。

2026.07.17 · 14 MIN READ

Harness 是 Agent 的工作环境

当模型要在真实任务中工作，它需要的不只是一次推理：还需要上下文装配、工具选择、执行状态、权限、观测、评测与恢复机制。Harness 就是把这些能力接在一起的运行环境。

把概念放回各自的位置

模型 / SDK生成与调用能力
Agent Loop计划、执行与修正
Harness上下文、工具、治理与观测

MCP 是工具与资源的标准接口；RAG 和 Memory 解决不同时间尺度的信息；Context Engine 决定当前任务到底带着哪些事实运行。它们都不是 Harness 的同义词，而是其中可能被组织和治理的部件。

用它检查产品是否真的可靠

  • 工具调用失败后，系统是否知道如何恢复或请求帮助？
  • 用户能否理解 Agent 当前的计划与证据来源？
  • 任务完成后，是否能留下可评测、可回放的记录？
